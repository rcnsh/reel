# reel

A deterministic WebGL video engine for agents. Every frame is a pure function of the time `t`, so the browser preview and the offline export (headless Chrome streaming frames over a WebSocket into ffmpeg) produce the same image, at any frame size and frame rate (16:9, vertical, square; `--scale 2` for true 4K), with adaptive motion blur. Stack: TypeScript, three.js, opentype.js, bun, Vite, playwright-core, ffmpeg; Python tools run through uv.

This repo is the engine and its `reel` CLI. A video is a **project**: a folder with a `reel.config.ts`, `scenes/` and its own audio and data, in this repo's `examples/` or anywhere else. It is a personal tool, adapted from [mexicat/pdoom-video](https://github.com/mexicat/pdoom-video). Build to that bar: working, tested, documented, no ceremony.

Where to read before acting:

- **Writing or changing a scene or a config**: `skills/reel-authoring/SKILL.md` and the reference files beside it (the Scene API, determinism and sampling rules, themes, the toolbox, timing); 3D in `skills/reel-3d/SKILL.md`. **Checking it**: `skills/reel-review-loop/SKILL.md`.
- **Changing the engine**: `docs/ENGINE.md` (the page, a frame's pipeline, adaptive sampling, readback, reporting).
- **Making a video, the layout, render commands**: `README.md`, and `bun cli/reel.ts --help` for every command and flag.
- **Briefing an agent to make a video** (the prompt's parts, a template): `PLAYBOOK.md`. A change to the MCP tools or to what an agent can deliver updates it.
- **A project's config**: the types in `src/config.ts` (`VideoConfig`, `Clip`). **Analysis flags**: `reel analyze --help`. **Mix config**: the comment at the top of `tools/mix.ts`.

## Words

- **Scene**: a class that draws (`scenes/<name>.ts` in a project). **Clip**: a scene placed on the timeline, with an id and a window. **Track**: a layer of clips; tracks stack in number order. **Project**: the folder holding a video's config, scenes and data.
- A narrated project's script is split into **plates** (`# name` headers in `narration.txt`); each becomes a section in `data/audio.json` and, through `clipsFromSections`, a clip shown by the scene of the same name.

## How the pieces connect

```
<project>/narration.txt ──reel narrate (a voice) or reel align (a recording)──▶ audio/narration.flac, data/words.json (words + times)
song ──reel analyze──▶ audio/<song>  +  data/audio.json  (beats, envelopes, onsets, sections, track)

<project>/reel.config.ts ─▶ format (size, fps) + timeline(): clips on tracks, each naming a scene module
cli/server.ts: Vite serving index.html + src/main.ts, with the project mapped in (@project, its files at the site root)
Engine.init ─▶ load the clips' scenes (+ the theme's overlay clip) ─▶ each frame: prepare (scenes' prepare(f), HTML layers updated,
            painted and uploaded when changed) ─▶ sub-frames: scenes render HDR into targets
            ─▶ transitions per track ─▶ track grades and mattes ─▶ tracks stacked (blend modes) ─▶ post (defaults from the theme)
src/main.ts: preview player (reel dev) or export API window.__reel (?export=1)
cli/reel.ts (flags: cli/args.ts) drives window.__reel through cli/renderer.ts + cli/ops.ts: info | still | sheet | strip | check | events | perf | gpu;
            cli/video.ts: the video export, cli/formats.ts: its output formats and ffmpeg commands
cli/review.ts + review.html: reel review, a Bun server on 127.0.0.1 for a person to watch a render and pin notes ─▶ <project>/review/notes.json
            (cli/notes.ts: the store, merged by id, atomic) ─▶ reel notes (list, add, done) and the MCP tools review_notes, resolve_note
reel video --mix (or reel events ─▶ data/cues.json ─▶ reel mix) + mix.json ─▶ the track (lossless), music and cues, two-pass loudness, one AAC encode
```

- The config is the edit. `size`, `fps` and `theme` are read by the CLI outside the browser (so a config's top level is plain data: scenes are lazy imports, engine calls live inside `timeline()`), and reach the page as the compile-time constants `__REEL_FORMAT__` and `__REEL_THEME__` (the theme resolved by `src/themes.ts`). Being constants, they are in place before any module runs, which is what lets `glsl/common.ts` bake the palette into shader strings at import time.
- The engine has no look of its own. The theme (`print`, `film`, `neutral` (the default) or an object) gives the palette, the post defaults and an optional overlay, which the engine places as a clip called `overlay` on a track above every other. The HUD (crop marks, captions) is an ordinary scene, `src/scenes/hud.ts` (`reel/scenes/hud`).
- Audio and words are optional. Without `data/audio.json` and `data/words.json` a project is silent, its sources are empty and its length is `duration` or the end of its last clip.
- `data/audio.json` `track` names the sound the preview plays and the export muxes (default `audio/narration.flac`). Without `--keep-sections`, `reel analyze` points it at the song.
- Scenes import the engine as `reel` (`src/index.ts`), configs import `reel/config` (`src/config.ts`), and both can name the engine's scenes as `reel/scenes/<name>` (`src/scenes/`): aliases in the dev server and `tsconfig.json`.
- An example's generated files are committed so it renders from a clone: `audio/narration.flac`, `data/words.json`, `data/audio.json`, `data/cues.json`. Regenerate them with their tool rather than editing them by hand.

## Rules

- **Deterministic.** A scene's output depends on `f.t` only. Randomness comes from `hash`/`mulberry32` with fixed seeds; per-frame jitter uses `frameIdx(t)`, which holds across a frame's shutter, and a frame step is `1 / FPS`, never `1 / 60`. `--samples auto` renders sub-frames out of order and in any number, so nothing may count `render()` calls. Simulation state means `stateful = true`, and the engine then refuses adaptive sampling (render such a video with a fixed `--samples N`).
- **Anchored to words.** Scenes find timing by text: `ctx.words.get('some words')` (throws when the line is missing, so a script edit fails loudly) and its word times. Times typed as numbers break the moment the voice is re-timed.
- **Logical pixels.** Scenes lay out in logical px, `W`×`H` (the `--size`, default 1920×1080), at every output scale; `PW`/`PH`, `gl_FragCoord`, `fwidth` and canvas backing sizes are physical. GLSL uses `FRAG_PX`, `PX_SCALE` and `pxLine` (`skills/reel-authoring/reference/sampling.md`, "Output scale").
- **Linear colour, from the theme.** Render targets are HalfFloat linear HDR. Colours come from the theme's palette (`src/engine/palette.ts`): `LIN.<key>` for GL, `C_<KEY>` in GLSL, `rgba('<key>', a)` for Canvas2D. Scenes meant to follow any theme use the keys every palette has: `bg`, `fg`, `accent`, `accentHi`, `accentLo`. The engine's own colours (flash, invert, heat ramp, spark, HUD) come from those keys too, never from a theme's extra keys.
- **Project-neutral engine.** `src/engine/` holds only what any video could use, and no look: colours and grades belong to themes (`src/themes.ts`). A video's own colours, story helpers, data and motifs live in its project (shared helpers as `scenes/_<name>.ts`, which `clipsFromSections` skips because no section is named `_…`).
- **Jitter by sub-frame, not by time.** Anti-aliasing, lens and area-light jitter index a low-discrepancy sequence with `SUB_FRAME.index` (`src/three/jitter.ts`), so every prefix of a frame's sub-frames is evenly spread. 3D with its own depth test draws into its own target after `ctx.maskDepth(rt)` (as `Stage3D` in `src/three/` does), never straight into `out`.
- **Text in HTML layers by default.** Text and layout go in an `HtmlLayer` (`src/engine/html.ts`), which reports itself to `reel check`; its content changes once per output frame (`update(f)` or the scene's `prepare(f)`), and motion that must blur goes in `draw()`'s transform. GL and Canvas2D are for pictures, shaders and strokes. Ready-made pieces (text blocks, kinetic text, title cards, captions, images, video clips, Lottie, charts, timers, code, drawn-on paths and arrows, and layout helpers) are the component kit in `src/kit/`, exported from `reel` and documented in `skills/reel-authoring/reference/kit.md`; a kit change updates that file.
- **Scenes report their text.** Text drawn with `fillText` is followed by `reportText(c, text, x, y)`, stroke-font text by `reportStrokeText`, other drawn text (glyphs, textures) by `report({ kind: 'text', … })`, so `reel check` can see it. Both are free outside a check; anything they need that costs work goes behind `if (reporting())`.
- **Upper tracks are transparent.** A scene on track 0 fully overwrites its target; a scene on a higher track clears it to transparent (`clearRT(renderer, out, [0, 0, 0], 0)`) and draws premultiplied over that, so the tracks below show through.
- **Sound by cue.** A scene that wants a sound calls `cue(kind, t)` in `init()`; `mix.json` maps kinds to files in `audio/`. Sounds placed on the timeline go in the config's `sounds` (or `sound()` from `init()`). Scenes never play audio.
- **Licences travel with the code.** `LICENSE` (upstream MIT, Giacomo Magnanini) covers the engine; `public/fonts/OFL-*.txt` and the stroke fonts' file headers cover the fonts. Keep them, and keep the upstream credit in `README.md` and `docs/ENGINE.md`.

## Tasks

`reel` below is `bun cli/reel.ts`; every command takes `--project <folder>`.

**New scene for a narrated plate.** Add the `# name` plate and its lines to the project's `narration.txt`, re-time (`reel narrate`: only the changed plate is voiced again), write `scenes/<name>.ts` default-exporting a `Scene` subclass (`examples/demo/scenes/hello.ts` is the minimal reference, a text block revealed as it is spoken; `written.ts` shows stroke text broken to the frame's width, word timing and cues), then typecheck and look at stills across the clip's window, including its last frame.

**New project.** `reel init <folder> [--size WxH] [--fps N] [--theme print|film|neutral] [--narrated]` writes one that renders straight away (it refuses a folder holding anything but `.git` or `.DS_Store`). Its `tsconfig.json` extends `tsconfig.project.json` here by absolute path (paths for `reel`, `reel/config`, `reel/scenes/*`, `three`; `project.d.ts` brings Vite's `import.meta.glob` types), so it typechecks without an install; its `package.json` scripts run this checkout's CLI and `tsc`. Change `tsconfig.project.json` with care: every project outside this repo extends it. `examples/layers` is a silent two-track project, `examples/explainer` a silent one built from the component kit, `examples/music` a music video cut to an analysed song, `examples/product3d` a 3D product shot, `examples/media` a vertical short of a video clip, an SVG and a Lottie, `examples/demo` a narrated one. For a real voice in a narrated project, time it: `reel align <recording>` (one take, or a folder of per-plate files named after the plates). Both take `--lead`, `--hold` and `--tail` (silence before the first word, between plates, after the last word), defaulting to `narration` in the config.

**Music video.** `reel analyze <song> --sections sections.json` with sections named after the scenes (`[{"name": "intro", "bar": 0}, …]`). Scenes react with `f.a` (envelopes and decaying kick/snare/hat/vocal pulses), `f.beat`, `f.bar`, `audio.hit`, `audio.env`. For cuts on the beat, snap clip starts in the config's `timeline()` with `src.audio.beatBefore(t)` or `src.audio.nearestDownbeat(t)`. Sung lyrics come from `reel align <vocal> --method whisper` (Whisper word times matched to the lyrics). `examples/music` is the reference.

**Narrated video with a music bed.** Time the narration first, then `reel analyze <bed> --keep-sections --offset <s>` to add the bed's beats from where it enters, and list the bed under `music` in `mix.json` with the same start (`"at": <s>`).

**Engine change.** Change `src/engine/` only for something any video could use. In the same change, update the `reel-authoring` skill for anything a scene author sees and `docs/ENGINE.md` for how it works inside; a fact lives in one of them, not both. After touching `engine.ts`, `gl.ts`, `post.ts` or `main.ts`, render a short `--samples auto` video as well as stills: the sampler, tile masking and readback paths only run on export.

**Skills.** `skills/<name>/SKILL.md` (YAML `name` and `description`) plus files beside it, each under about 300 lines; long reference goes in the files. They are written for a capable agent that has never seen reel and carry knowledge, not process. Projects hold copies (`reel init`, `reel skills update`), so a skill must make sense without this repo.

**Fonts.** A project's fonts are the files in its `fonts/` folder (`cli/fonts.ts` describes them with fontkit; `reel font add "<family>"` fetches a Google Fonts family there with its licence). The engine's own: `uv run tools/make_fonts.py` cuts the static instances from `public/fonts/src/`. Its instance lists and `src/engine/type.ts` (`ARCHIVO_WIDTHS`, `ARCHIVO_WEIGHTS`, `DEFS`) must match. Regenerated files differ from the committed ones only in the `head` table, so an unchanged rebuild needs no commit.

## Checks

Run all that apply before reporting work done:

1. `bun run typecheck`: one tsconfig over `src/`, `cli/`, `tools/`, `examples/` and `tests/`; then `bun test`.
2. Stills of every clip you touched, looked at with the Read tool: `reel still --project <p> --t <times> --only <clip>`. `reel sheet --cuts` checks every cut at once.
3. Theme or post changes: the print theme must still render the demo byte for byte as before. Stills before and after (`reel still --project examples/demo --t 0.4,2.5,5,6.9`) compared with a pixel diff.
4. Export path changes: every example end to end. `reel video --project examples/demo --samples auto --preset veryfast --out <raw.mp4>`, then `reel events`, then `reel mix <raw.mp4> <out.mp4>` (it prints the LUFS and true peak), and `reel video --mix` once; `reel video --project examples/layers --samples auto --preset veryfast` (tracks, a wipe, the film theme's overlay, no audio, vertical, 30 fps); and `reel video --project examples/explainer --samples auto --preset veryfast` (the kit, every transition kind, an image); `reel video --project examples/music --samples auto --preset veryfast` (a song as the track, square); `reel video --project examples/product3d --samples auto --preset veryfast` (a 3D stage: a glTF model and its animation, depth of field, soft shadows, text on a plane); `reel video --project examples/media --samples auto --preset veryfast --mix` (a decoded video clip with its sound in the mix, an SVG, a Lottie, vertical). Format changes: `bun test tests/video-formats.test.ts` renders a second in every format family and checks the streams with ffprobe; extract frames from the files and look at them (over a checkerboard for alpha).
5. `reel init`, `tsconfig.project.json` or `project.d.ts` changes: `reel init` a silent and a `--narrated` project under `/tmp`, then in each `bun run typecheck`, `bun run reel still --t 1` and `bun run reel video --samples auto --preset veryfast`.
6. Python tool changes: run the tool on real input. For `analyze.py`, `tools/synth_song.py` makes songs with known beats: a lead-in, a break, a non-integer tempo, a half-time feel and a drifting tempo are the cases that have broken it before; compare `data/audio.json`'s beats and downbeats with its JSON, for the default path and `--fast` (`tests/analyze.test.ts` does it for `--fast`). For narration, `say` per word concatenated gives words with exact boundaries to measure the aligner against.

`bun test` runs the tests in `tests/`: unit tests of the pure modules (words, audio, config, themes, flags, check's measurements, PNG diffing, word alignment, the mix's filter graph, transitions, the kit's helpers and layout maths) in well under a second, and the slower ones that need Chrome (`reel chrome install`, or `CHROME_PATH`; they skip without one): golden frames, the CLI end to end (`tests/cli.test.ts`: exit codes, still naming, diff, check, init, the warm renderer), the kit's components through check and a seek (`tests/kit.test.ts`) the MCP client and the exports in every format, about 75 s in all (the video formats about 25 s, the CLI about 18 s; more on a busy machine); and `reel analyze --fast` on synthesised songs (`tests/analyze.test.ts`: beats, downbeats and kicks within milliseconds of their known times in check 6's cases; it skips without uv, or until uv has the tools' packages: run `reel analyze --fast` once). Rendering tests work on scratch copies of the examples in the temp folder and stop their warm renderers. `tests/setup.ts` (preloaded through `bunfig.toml`) gives the run an export slot of its own (`REEL_EXPORTS_DIR` in a temp folder), so another agent's export on the machine neither fails nor queues the tests'. Run it before every commit; run the unit files alone (`bun test tests/words.test.ts`) while working. A test that pins a behaviour you changed on purpose gets updated in the same commit.

The golden test renders the frames listed in `tests/golden/goldens.json` (small stills of the examples, one with `--samples auto`, one vertical, one in another theme) and compares them with the committed PNGs for the operating system (`tests/golden/darwin/`, `tests/golden/linux/`: Chrome rasterises text and decodes video differently on each, so each has its own set; the Linux one is rendered by SwiftShader), allowing 3 levels of noise. When it fails, the message gives the changed pixels and where. A change meant to alter how the examples look: run `reel golden update` on the Mac and on a Linux machine (the InstaBox box), copy the Linux PNGs back, Read the new PNGs, and commit them with the change. A change not meant to: the failure is the bug. The tests prove the parts; the renders above still prove the video.

## Environment and gotchas

- **Chrome.** `cli/chrome.ts`: renders use `CHROME_PATH`, else the pinned Chrome for Testing build (`CHROME_BUILD`) in reel's cache folder (`~/Library/Caches/reel-chrome` here; `reel chrome install` fetches it with `@puppeteer/browsers`). Never the installed Google Chrome. A browser older than 157 (no HTML-in-Canvas) is refused after launch with a message naming the fix. Leave `CHROME_PATH` unset on this Mac. WebGL goes through ANGLE on a backend `glBackend()` picks: Metal on macOS; on Linux EGL when there is a GPU render node, else SwiftShader (software); `--gl` or `REEL_GL` overrides, and `--json` reports it as `gl`. Two launches of one Chrome can differ by a pixel or two of Canvas2D text by 2 to 3 levels (GPU text raster); one page is byte-identical from render to render, and the goldens allow 3 levels.
- **Workspaces.** A project inside a monorepo can import its workspace's sources and packages: the dev server's `fs.allow` adds Vite's `searchForWorkspaceRoot(project)`. `tests/cli.test.ts` covers a project in a pnpm workspace whose scene and a package's `?inline` stylesheet sit outside the project folder.
- **Dev server.** Every rendering command (or its warm renderer) uses a Vite of its own on a free port, without live reload, so a render never talks to another project's server and a file saved mid-render does not reload the page. `reel dev` is the one with live reload. Each project's servers share a Vite cache of their own (`node_modules/.vite/reel/`), so renders of different projects at once do not disturb each other; a package `src/` newly imports goes in `PREBUNDLED` (`cli/server.ts`), or `tests/server.test.ts` fails.
- **Warm renderer.** `info`, `still`, `sheet`, `strip`, `check`, `diff --t`, `events`, `perf` and `gpu` run in a background process per project (`cli/daemon.ts`) that keeps Vite, Chrome and pages open: a warm still takes about 0.15 s. Before every request it stats the project's files and the modules Vite loaded from outside the project, packages and the engine aside (not a file watcher, which can deliver an edit after the request that follows it), and reloads its pages, and Vite's modules for the changed files, when any changed. Its state, token and log are in `$TMPDIR/reel-daemons/` (`reel daemon status` prints the log path). A request is plain data with absolute paths (`cli/ops.ts`), so ops work the same in it and with `--no-daemon`. It is replaced when the engine's code (`src/`, `cli/`, `index.html`, `package.json`) or the Chrome it would launch changes, so after editing the engine the next command pays a cold start. Debug the page path with `--no-daemon`; stop stragglers with `reel daemon stop --all`.
- **MCP.** `reel mcp` (`cli/mcp.ts`) maps tools onto the same requests as the CLI (`reqOf` checks arguments with the CLI's flag rules, and an argument a tool does not have is an error) and sends them to the warm renderer; video jobs run `reel video --json --progress` as child processes. Nothing may write to stdout in that process except the MCP transport.
- **Stills** are named after the clips on screen and the time (`out/stills/hello_2.500s.png`), and a name that is taken gets `-2`, `-3`: stills never overwrite each other. `--out <file.png>` writes exactly that file.
- **Exit codes.** 0: done and no scene reported an error. 1: something failed (a scene's `init()` or `render()` threw, a shader did not compile, ffmpeg, the page). 2: bad command line or no project. `--json` puts the same in `{ ok, errors, logs }`. A scene that throws in `render()` shows as a dark red frame.
- **Flags are strict.** An unknown flag is an error; `reel --help` is the list.
- **Preview.** `reel dev --project <p>`, then the URL it prints (5173 when free, else the next free port), with `?t=<seconds>`. Space plays, arrow keys seek, `,`/`.` step a frame, `[`/`]` jump clips, `l` loops the clip, `h` hides the UI. A missing track still plays silently: the clock runs on `performance.now()`.
- **`--only a,b`** loads only those clips: faster, and isolates you from another scene's errors. Clips that are not loaded draw nothing; `check` samples only the loaded clips' frames and leaves the others out of its findings.
- **Stateful scenes** (`stateful = true`) are exported by one worker in order, whatever `--workers` says, and refuse `--samples auto`.
- **Partial renders and the mix.** `reel mix --from <s>` must match the render's `--from`, or cues and music land in the wrong place.
- **analyze.py** copies the song into the project's `audio/` under a URL-safe name (the preview fetches it by URL). Its models run in `tools/music_models.py`, a uv environment of their own (torch for Beat This!; Demucs through MLX on Apple Silicon, PyTorch elsewhere), so `--fast` (librosa only) installs neither. The Beat This! checkpoint comes from the authors' server or, when that is down (it has been), the mirror one of them hosts, checked against their MD5. `--onset-delta` tunes the peak-picking per drum band.
- **Frame size.** `size` wants a width that is a multiple of 4 and an even height (the packed readback and yuv420). A scene written for one aspect does not reflow by itself: lay out from `W` and `H`, not from 1920 and 1080.
- **Disk.** A project's `out/` fills fast (a 4K render is gigabytes), and the video command spools up to `--spool-gb` (default 20) of frames to the system temp folder while x264 catches up.
- **Outputs are atomic.** Every file an export or the mix writes goes to a partial beside it (`<name>.partial-<pid>-<ms><ext>`, `cli/scratch.ts`) and is renamed onto `--out` once finished; never point ffmpeg straight at `--out`. A render with scene errors keeps the previous output. Scratch names carry their pid, so the next export sweeps a killed export's spools, frame folders and the partials in its output folder (`reel daemon stop --all`: the temp folder's), without touching a live one's (a pid counts as gone when it is dead or now runs something other than bun).
- Bun 1.4, TypeScript 7 (`tsc` comes from the `typescript` peer dependency), three.js 0.186, Vite 8 (started from the CLI through its API; there is no `vite.config.ts`). Python tools pin their dependencies inline (PEP 723); `uv run` fetches them on first use.

## Git

Every change is committed straight to `main`, one logical change per commit: no branches, no PRs. Conventional Commits (`feat(analyze): …`, `fix(mix): …`, `docs: …`), title only: no body and no trailers. A change large enough to want review gets a fresh-context review of the diff before it is committed. Keep `README.md`, `docs/ENGINE.md`, the skills, `reel --help` (`cli/args.ts`) and this file current in the same commit as the behaviour they describe.
