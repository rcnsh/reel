# Child processes are killed by a watchdog reading a pipe

A process killed by a signal it does not handle (SIGALRM from a `perl -e 'alarm N; exec …'` time limit, SIGQUIT, SIGKILL) runs no cleanup of its own, and macOS has no parent-death signal. Before the watchdog, a killed reel left its ffmpeg (or uv and the Python under it) running, which then ignored a later SIGTERM mid-graph.

`cli/children.ts` (`spawnChild`, `startWatchdog`, `WATCHDOG`) registers every child with one `/bin/sh` watchdog per reel process. The watchdog runs in a process group of its own, so a Ctrl-C to reel's group does not end it first. It reads `+<pid>` and `-<pid>` lines from a pipe whose only writer is reel. When reel ends, however it ends, the kernel closes that pipe. The watchdog then sends SIGTERM to every child still registered and everything under it (uv's Python, the Python's own subprocesses), waits up to `KILL_AFTER_S` for them to go, and sends SIGKILL. The watchdog process and its stdin are `unref`'d: reel's exit is what it waits for, so it must not keep reel's event loop alive. The script is POSIX sh: dash, which is `/bin/sh` on Debian, takes no `--` after kill's signal.

Children stay in reel's process group, so the terminal's Ctrl-C and Ctrl-Z reach them as before. For a project tool (`cli/reel.ts`, the `TOOLS` path), reel waits while the tool cleans up after a stop, rather than ending first and having the watchdog cut that cleanup short. The terminal's Ctrl-C and hang-up reach the tool by themselves, a SIGTERM is passed on, and reel gives up waiting after a few seconds.
